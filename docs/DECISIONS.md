# Architecture Decisions

결정 형식은 날짜, 상태, 배경, 결정, 영향 영역, 장점, 주의사항, 재검토 조건 순서로 기록한다.

## 프로젝트명 MS FlowHub

- 날짜: 2026-07-30
- 상태: 채택
- 배경: 통합 업무 흐름을 드러내는 포트폴리오 이름이 필요하다.
- 결정 내용: 가상 회사는 MS, 프로젝트는 MS FlowHub로 통일한다.
- 영향을 받는 영역: 전체 문서와 UI
- 장점: 일관된 정체성
- 주의사항: Microsoft 제품으로 오인되지 않게 가상 회사임을 밝힌다.
- 이후 재검토 조건: 공개 전 상표·명칭 검토

## 전자결재 중심의 모듈형 구조

- 날짜: 2026-07-30
- 상태: 채택
- 배경: 채용 요청과 할인 승인이 같은 승인 규칙을 공유한다.
- 결정 내용: 전자결재를 공통 엔진으로 두고 ATS Lite와 CRM Lite를 연결한다.
- 영향을 받는 영역: 서비스, 데이터, API
- 장점: 규칙 재사용과 통합 시연
- 주의사항: 모듈 간 순환 의존을 피한다.
- 이후 재검토 조건: 다단계 결재 도입

## Next.js와 FastAPI 분리

- 날짜: 2026-07-30
- 상태: 채택
- 배경: UI와 업무 규칙의 책임을 분리한다.
- 결정 내용: Next.js App Router 프론트엔드와 FastAPI 백엔드를 별도 앱으로 둔다.
- 영향을 받는 영역: 전체 구조
- 장점: API 경계와 학습 목표가 명확하다.
- 주의사항: 공통 API Client와 CORS 설정 필요
- 이후 재검토 조건: 배포 구조 확정

## Supabase PostgreSQL과 API 접근 경계

- 날짜: 2026-07-30
- 상태: 채택
- 배경: 관리형 PostgreSQL을 사용하되 업무 규칙을 우회하면 안 된다.
- 결정 내용: Supabase PostgreSQL을 메인 DB로 사용하며 프론트엔드는 업무 테이블에 직접 접근하지 않고 FastAPI만 호출한다.
- 영향을 받는 영역: DB, 보안, 프론트엔드
- 장점: 업무 규칙과 비밀정보의 서버 집중
- 주의사항: DB 접속정보를 프론트에 노출하지 않는다.
- 이후 재검토 조건: Supabase Auth 도입

## SQLAlchemy 2.0 동기 방식과 Alembic

- 날짜: 2026-07-30
- 상태: 채택
- 배경: 초급 학습 범위를 관리하고 스키마 이력을 보존한다.
- 결정 내용: Psycopg 3, SQLAlchemy 2.0 동기 Session을 사용하고 모든 스키마 변경을 Alembic으로 기록한다.
- 영향을 받는 영역: Backend, DB, 테스트
- 장점: 단순한 실행 흐름과 재현 가능한 DB
- 주의사항: 대시보드 수동 변경을 migration 없이 남기지 않는다.
- 이후 재검토 조건: 동시성·성능 요구 증가

## 실제 인증 대신 역할 전환

- 날짜: 2026-07-30
- 상태: 채택
- 배경: 프로토타입은 핵심 업무 흐름에 집중한다.
- 결정 내용: 샘플 직원 ID로 현재 사용자를 선택하되 서비스가 직원과 역할을 DB에서 재조회한다.
- 영향을 받는 영역: UI, 권한, API
- 장점: 역할별 시연이 빠르다.
- 주의사항: 실제 인증이 아니며 운영에 사용할 수 없다.
- 이후 재검토 조건: 프로토타입 이후 인증 마일스톤

## 프로젝트 운영자 전 부서 기안 예외

- 날짜: 2026-07-30
- 상태: 채택
- 배경: 포트폴리오 시연에서 프로젝트 운영자가 각 부서의 전자결재 흐름을 하나의 샘플 계정으로 확인해야 한다.
- 결정 내용: 샘플 관리자 김민성은 전 부서를 기안할 수 있다. 관리자가 아닌 직원은 자신의 소속 부서에만 기안할 수 있다.
- 영향을 받는 영역: 전자결재 작성·수정 Service, 작성 화면, 샘플 직원 데이터
- 장점: 시연 편의성을 확보하면서 일반 역할의 부서 권한 규칙은 유지한다.
- 주의사항: 실제 운영 권한 모델로 사용하지 않으며, 인증 도입 시 권한 정책으로 대체한다.
- 이후 재검토 조건: 실제 인증·조직 권한 모델 도입

## 관리자 전용 전자결재 삭제

- 날짜: 2026-07-31
- 상태: 채택
- 배경: 시연 데이터와 실수로 생성된 문서를 관리자가 정리할 수 있어야 한다.
- 결정 내용: 문서 상태와 작성자와 관계없이 `ADMIN` 역할만 전자결재를 물리 삭제한다. 일반 역할은 본인이 작성한 문서도 삭제할 수 없다.
- 영향을 받는 영역: 전자결재 목록·상세 화면, 삭제 API, Service 권한 규칙
- 장점: 역할 부여만으로 삭제 권한을 일관되게 관리할 수 있다.
- 주의사항: 물리 삭제는 이력도 제거하므로 운영 환경에서는 감사 로그 또는 soft delete를 재검토한다.
- 이후 재검토 조건: 실제 인증 및 감사 로그 요구사항 확정

## 단일 결재자와 자기 결재 금지

- 날짜: 2026-07-30
- 상태: 채택
- 배경: 최소 결재 흐름과 권한 분리를 동시에 보여준다.
- 결정 내용: 프로토타입은 결재자 한 명만 지원하고 작성자와 결재자가 같으면 상신을 거부한다.
- 영향을 받는 영역: Approvals, Seed, 테스트
- 장점: 규칙이 명확하고 이해하기 쉽다.
- 주의사항: 대리·위임·다단계 결재는 없다.
- 이후 재검토 조건: 조직별 결재선 도입

## 할인 기준 이하 견적의 직접 확정

- 날짜: 2026-07-30
- 상태: 채택
- 배경: 모든 견적에 결재를 요구하면 기준 설정 의미가 약해진다.
- 결정 내용: 10% 이하는 서버 재계산 후 결재 없이 확정 가능하고, 초과 시 승인 전 확정을 금지한다.
- 영향을 받는 영역: Quotations, Approvals, 설정
- 장점: 대표 조건 분기를 명확히 시연한다.
- 주의사항: 기준값은 `DISCOUNT_APPROVAL_THRESHOLD`로 중앙 관리한다.
- 이후 재검토 조건: 상품·직급별 승인 규칙

## 공통 MockAIProvider와 인간 검토

- 날짜: 2026-07-30
- 상태: 채택
- 배경: API 키 없이 시연하고 AI 중복 구현을 막아야 한다.
- 결정 내용: 공통 Provider 인터페이스와 MockAIProvider를 제공하고 원본·생성·최종 수정 결과를 공통 `ai_generations`에 저장한다.
- 영향을 받는 영역: AI, ATS, CRM, DB
- 장점: 교체 가능성과 재현 가능한 시연
- 주의사항: AI는 최종 판단·상태 변경·발송을 수행하지 않는다.
- 이후 재검토 조건: 실제 Provider 품질 및 비용 검증

## Supabase 미설정 시 로컬 영속 저장소

- 날짜: 2026-07-30
- 상태: 채택
- 배경: Supabase 접속정보가 없어도 전자결재 저장·새로고침 흐름을 개발하고 시연해야 한다.
- 결정 내용: `DATABASE_URL`이 없으면 동일 SQLAlchemy 모델을 파일 기반 SQLite에 저장하고, 설정되면 Supabase PostgreSQL을 사용한다.
- 영향을 받는 영역: DB Session, Repository, 로컬 실행, 테스트
- 장점: 외부 접속정보 없이 실제 CRUD와 상태 유지 가능
- 주의사항: SQLite는 로컬 개발 fallback이며 메인·배포 DB가 아니다. Supabase에는 Alembic을 먼저 적용한다.
- 이후 재검토 조건: Supabase 개발 프로젝트 연결 완료
