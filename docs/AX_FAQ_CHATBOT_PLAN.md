# AX 직원 도우미 v1 기능 명세

> 2026-08-09 전면 재작성. 1차 기획(단계별 누적 방식)에서 범위·기술설계·합격기준이 서로 어긋나는 문제가 발견되어, 제약 조건에서 거꾸로 설계하는 방식으로 다시 작성했다.

## 0. 설계 전제

이 기능의 성격을 규정하는 두 가지 사실이 먼저 있고, 나머지 설계는 전부 여기서 파생된다.

1. **v1은 LLM을 호출하지 않는다.** 등록된 매뉴얼·FAQ 중 질문에 맞는 것을 찾아 원문을 보여주는 방식이다.
2. **지식 원천은 매뉴얼 9개 + FAQ 21개, 총 30개 문서뿐이다.** (FAQ는 이 기획에 따라 18→21건으로 보강했다. 9장 참조)

여기서 따라 나오는 결론:

- 문서에 없는 내용은 **구조적으로 답할 수 없다.** 따라서 "답할 질문"을 먼저 정하는 게 아니라 **"문서로 답이 되는 질문"만 범위에 넣는다.** 문서가 없으면 문서를 먼저 추가한다.
- RAG·벡터DB·임베딩은 도입하지 않는다(30개 규모에 인프라 이득 없음).
- **UI에서 이 기능을 "AI"라고 부르지 않는다.** 명칭은 "MS FlowHub 도우미". LLM을 쓰지 않는데 AI라 부르면 사용자가 자연어 이해 수준을 과대평가해 실패 경험이 늘어난다.
- 가장 큰 리스크는 "답을 못 찾는 것"이 아니라 **"엉뚱한 문서를 근거로 자신 있게 오답하는 것"**이다(→ 3장·4장이 이 문제를 정면으로 다룬다).

## 1. 범위

| 구분 | 내용 | v1 |
|---|---|---|
| 문서 기반 답변 | 매뉴얼·FAQ 원문으로 답 가능한 질문 | **포함(19문항)** |
| 정책 고정 응답 | "AI가 결재를 대신 처리하나요?"류 | **포함(1문항)** |
| 화면 이동 | 답변 카드에서 관련 화면으로 가는 **링크 제공** | 포함 |
| 매뉴얼 상세 페이지 | `/manuals/{slug}` 읽기 전용 페이지 신설 | **포함**(사유는 3장 참조) |
| 자동 화면 전환·데이터 조작 | AI가 대신 클릭·저장 | **제외(영구)** |
| 실시간 업무 데이터 조회 | "진행 중 공고 몇 건?" 등 | **제외 → v2** |
| 개인화 데이터 | "내 결재 대기 몇 건?" 등 | **제외 → v2** |

`[조회]`·`[개인화]`를 v1에서 뺀 이유: 이 둘은 `Manual`/`ManualFaq`가 아니라 `Employee`·`Team`·`JobPosting`·`ApprovalDocument` 조회가 필요하다. 즉 **지식 검색이 아니라 업무 데이터 API**이고, 권한 설계·오답 리스크·테스트 범위가 전부 달라진다. v1에 섞으면 기능 하나에 성격이 다른 두 시스템이 들어간다.

**미사용 FAQ**: FAQ 21건 중 `login-401`(401 오류) 1건만 질문 목록에 없다. 검색으로는 도달 가능하므로 그대로 둔다.

### A4가 특별히 위험한 이유 (해결됨, 근거로 보존)

`man:recruitment-request-to-posting` 본문에 **"포스터 첨부 … JPG, PNG, WEBP, PDF 형식에 5MB 이하만 첨부할 수 있으며"**가 상세히 적혀 있다. 반면 전자결재 문서 어디에도 "첨부"라는 단어가 없었다(전체 문서에서 "첨부" 언급은 채용 관련 2곳뿐). 따라서 "전자결재에 파일을 **첨부**할 수 있나요?"를 단순 키워드 매칭하면 채용 매뉴얼이 최상위로 걸리고, **"네, 첨부할 수 있습니다"라는 명백한 오답**이 나갔다. 실제로는 `ApprovalDocument` 모델에 첨부 컬럼 자체가 없다.

→ 그래서 `faq:approval-attachment`는 "지원하지 않는다"만 쓰지 않고 **채용 포스터 첨부와 명시적으로 구분해 주는 문장**을 포함했다. 이 한 건이 4장 오매칭 방지 설계 전체의 시험대이며, 8장 하드 게이트에서 반드시 확인한다.

### v2 확장 후보 (설계만 기록, 구현 안 함)

`[개인화]` 내 결재 대기 건수 / 내가 상신한 반려 문서 / 내 상급자 / 우리 부서 오늘 근태 · `[조회]` 특정 팀 구성원 / 부서별 팀 수 / 진행 중 공고 수

## 3. 답변 유형 (5종)

응답은 반드시 아래 5종 중 하나다. 그 외 자유 서술은 없다.

| 유형 | 조건 | 표시 |
|---|---|---|
| **확정 답변** | 최고점 ≥ 확신 임계값 **그리고** 2위와 점수 차 ≥ 마진 | 원문 + 근거 링크 + 화면 이동 버튼 |
| **후보 제시** | 최고점은 넘었으나 2위와 접전 | "이 중 어떤 걸 찾으시나요?" + 후보 2~3개 버튼 |
| **근거 없음** | 최고점 < 하한 임계값 | 고정 문구: "관련 매뉴얼이나 FAQ를 찾지 못했습니다. 인사팀 또는 관리자에게 문의해 주세요." |
| **정책 고정** | 정책 키워드 룰 선매칭 | 하드코딩 문구(검색보다 우선, 아래 참조) |
| **v2 안내** | 개인화·실시간 조회 의도 감지 | "이 항목은 도우미가 답변하지 않습니다. [해당 화면]에서 직접 확인해 주세요." + 링크 |

**"v2 안내" 감지 방법**: 자유 추론이 아니라 좁은 명시적 룰만 쓴다. 1인칭·소유 표현(`제/내/우리`)과 수량·현황 표현(`몇 건`, `몇 명`, `누구`, `현황`, `목록`)이 **함께** 나타날 때만 발동한다. 애매하면 발동시키지 않고 일반 검색으로 넘겨 "근거 없음"으로 떨어지게 한다 — 과잉 발동으로 답할 수 있는 질문까지 막는 쪽이 더 나쁘기 때문이다.

**"후보 제시" 유형이 이 설계의 핵심**이다. 1차 기획은 확정/실패 2가지뿐이라 애매한 경우 무조건 한쪽으로 확신해야 했고, 그게 A4 같은 오답을 만든다. 접전이면 확신하지 않고 사용자에게 고르게 하는 것이 정답률·체감 품질 모두에 낫다.

### 표시 규칙

- **FAQ가 근거일 때**: `answer` 원문 그대로 표시(이미 2~3문장으로 정리돼 있음). FAQ에 `related_manual_id`가 있으면 그 매뉴얼로 "자세히 보기"를 건다.
- **매뉴얼이 근거일 때**: `summary`(최대 500자)를 표시하고 `content`는 **검색에만** 사용한다. 장문 `content`를 채팅창에 그대로 쏟지 않는다. 전문은 "자세히 보기" 링크(`/manuals/{slug}`)로 연결.
- 근거는 **문서 제목 + 카테고리**를 항상 함께 표시한다.

#### 매뉴얼 상세 페이지를 v1에 포함하는 이유

현재 프론트에는 **매뉴얼 상세 페이지가 없다.** 라우트는 `/manuals`(목록)와 `/manuals/{slug}/edit`(관리자 전용)뿐이고, 목록 카드는 `title`과 `summary`만 렌더링한다(`frontend/src/features/manuals/manual-list.tsx`). 즉 **일반 직원은 앱에서 매뉴얼 본문을 읽을 방법이 없다**(PDF 다운로드가 유일).

이 상태로 "자세히 보기"를 목록으로 보내면 챗봇에서 이미 본 `summary`가 그대로 다시 나와 링크가 무의미해진다. 또한 4장은 `content`를 검색 대상에 넣는데 표시는 `summary`만 하므로, **검색된 근거와 보여주는 내용이 어긋나** 사용자가 "왜 이 문서지?"를 이해할 수 없다.

→ 읽기 전용 `/manuals/{slug}` 페이지를 v1 범위에 포함한다. 백엔드 `/api/v1/manuals/{slug}`와 프론트 `getManual(slug)`가 **이미 존재**하므로 백엔드 작업은 없고 프론트 페이지 하나만 추가하면 된다. 챗봇과 무관하게도 메워야 할 제품 공백이다.

#### 화면 이동 버튼 — 카테고리 이름 정규화

**주의: FAQ와 매뉴얼은 카테고리 이름 체계가 다르다.** 문자열 정확일치로 매핑하면 한쪽이 누락된다.

| 도메인 | FAQ 카테고리 | 매뉴얼 카테고리 | 이동 라우트 |
|---|---|---|---|
| 전자결재 | `전자결재` | `전자결재` | `/approvals` |
| 직원·조직 | `직원·조직` | `직원·조직 관리` | `/employees` |
| 근태 | `근태·휴가` | `근태·휴가` | `/employees` |
| 채용 | `채용 요청·ATS` | `채용 요청·ATS Lite` | `/recruitment-requests` |
| 로그인 | `로그인·계정` | `로그인·계정` | 버튼 없음 |
| 권한 | `권한` | (없음) | 버튼 없음 |
| 일반 | `일반` | `업무 홈 대시보드` | `/` |

구현 시 **도메인 → 카테고리 집합** 매핑 한 곳으로 관리하고, 라우트와 4장 부스트가 같은 매핑을 공유한다.

### 정책 고정 응답 (F2)

> "아니요. 이 도우미는 등록된 매뉴얼과 FAQ에서 안내 문서를 찾아 보여줄 뿐이며, 결재 승인·반려나 지원자 합격·불합격 같은 업무 처리는 하지 않습니다. 모든 업무 처리는 담당자가 직접 화면에서 수행합니다."

v1엔 LLM이 없다는 사실까지 정직하게 반영한 문구다. 검색 스코어링보다 **먼저** 평가한다.

## 4. 매칭 방식

### 토크나이저: 글자 단위 bigram (형태소 분석기 미사용)

한국어 형태소 분석(konlpy/mecab)은 시스템 바이너리 의존성이 붙고 배포가 복잡해진다. 문서 30개 규모에서는 **글자 bigram 집합 비교**가 의존성 0으로 동등하거나 더 낫다("결재를" / "결재는" 같은 조사 변화에도 강함).

### 스코어링

1. 질문·문서를 정규화(공백·문장부호 제거, 소문자화) 후 글자 bigram 집합으로 변환
2. 필드 가중치를 준 Dice 계수 합산 — `FAQ.question` ×3, `Manual.title` ×3, `Manual.summary` ×2, `FAQ.answer` ×1, `Manual.content` ×1
3. **카테고리 부스트**: 질문에 도메인 키워드가 있으면 해당 **카테고리 집합**에 속한 문서에 ×1.5

| 질문 속 키워드 | 부스트 대상 카테고리 집합 |
|---|---|
| 결재 / 전자결재 / 상신 / 반려 / 승인 | `전자결재` |
| 근태 / 휴가 / 연차 / 반차 / 병가 / 출근 | `근태·휴가` |
| 채용 / 지원자 / 공고 / 전형 / 면접 | `채용 요청·ATS`, `채용 요청·ATS Lite` |
| 직원 / 조직도 / 부서 / 사번 / 팀 | `직원·조직`, `직원·조직 관리` |
| 로그인 / 비밀번호 / 세션 | `로그인·계정` |
| 권한 / 403 / 401 / 메뉴 | `권한` |
| 기능 / 사용법 | `일반`, `업무 홈 대시보드` |

**반드시 집합으로 매핑해야 한다.** FAQ와 매뉴얼의 카테고리 이름이 다르기 때문이다(`직원·조직` vs `직원·조직 관리`, `채용 요청·ATS` vs `채용 요청·ATS Lite`). 단일 문자열로 적으면 한쪽이 통째로 부스트에서 빠진다.

또한 **권한 질문(E3·E4)은 `로그인·계정`이 아니라 `권한` 카테고리**다. `permission-403`·`permission-missing-menu`·`permission-401`이 모두 `권한`에 속하므로, 403/401을 로그인 쪽으로 부스트하면 정답 FAQ가 밀려난다.

카테고리 부스트가 **A4 오매칭을 막는 주 장치**다. "**전자결재**에 파일을 첨부할 수 있나요?"는 `전자결재` 카테고리가 부스트되어, `faq:approval-attachment`가 채용 매뉴얼을 이긴다.

### 검색 계층은 교체 가능하게 분리한다

API 핸들러가 매칭 로직을 직접 호출하지 않고, **"질문 + 후보 문서 → 점수순 결과"** 형태의 검색기(searcher)를 거치게 한다. v1은 키워드 검색기 하나만 구현한다.

이렇게 두는 이유는 v2에서 임베딩 기반 검색으로 갈아끼울 때 **API·응답 유형·프론트를 그대로 두기 위해서**다. 지금 분리해두는 비용은 함수 경계 하나뿐이라 사실상 0이지만, 나중에 섞여 있으면 API까지 손대야 한다. 반대로 지금 임베딩을 미리 만들어두지는 않는다(필요해지기 전에 만들지 않는다는 원칙과 동일).

### 임계값

확신 임계값·하한 임계값·마진의 **구체 수치는 지금 정하지 않는다.** 실측 없이 정한 숫자는 근거가 없다. 대신 절차를 정한다:

1. 구현 후 2장 20문항 + 오답 유도 질문(첨부/기능/신청 등 함정 표현) + 무관 질문 5개를 입력해 점수 분포를 뽑는다.
2. **오답 0건**을 최우선 제약으로 두고 임계값을 정한다(애매하면 확정 대신 후보 제시로 떨어지게).
3. 확정된 수치와 20문항 기대 결과를 **자동화 테스트로 고정**해 이후 회귀를 막는다.

## 6. 데이터·권한

- **지식 원천**: `Manual`(`status="PUBLISHED"`) + `ManualFaq`(`is_published=true`). 질의 시점에 원본 테이블을 직접 조회하므로 문서를 고치면 즉시 반영된다(별도 색인·캐시·재색인 트리거 불필요 — 임베딩을 안 쓰기로 한 데서 오는 이득). **단 v1.1에서 캐시를 도입하면 이 즉시성이 깨진다** — 트레이드오프는 11장 참조.
- **권한 필터**: 사용자 `role`이 `Manual.target_roles`에 없으면 **조회 쿼리 단계에서 후보에서 제외**한다(응답 생성 후 걸러내지 않음). 기존 `backend/app/api/dependencies.py` 권한 패턴을 재사용하고 새 권한 체계를 만들지 않는다.
- `ManualFaq`에는 권한 필드가 없다 → v1에서 FAQ는 전부 공개로 취급. 관리자 전용 FAQ가 실제로 필요해지기 전에는 컬럼을 추가하지 않는다.
- **읽기 전용**: AX API는 `Manual`·`ManualFaq`·`Employee.role`만 읽는다. 결재·근태·채용 데이터를 읽지도 쓰지도 않는다.
- **장애 대응**: v1엔 외부 AI 호출이 없으므로 실패 모드는 DB/API 오류뿐이다. 이 경우 오류를 감추지 않고 "지금 도우미를 사용할 수 없습니다"와 함께 `/faq`·`/manuals` 링크를 안내한다.

## 7. 로깅과 프라이버시

품질 개선에 필요한 최소 항목만, 전용 경량 테이블 `ax_chat_logs`에 남긴다.

| 컬럼 | 내용 |
|---|---|
| `question_text` | 사용자가 입력한 질문 원문 |
| `result_type` | 확정 / 후보제시 / 근거없음 / 정책 / v2안내 |
| `matched_type`, `matched_id` | 근거 문서 종류와 ID |
| `top_score` | 최고 점수(임계값 튜닝용) |
| `top_candidates` | **상위 3개 후보의 문서 ID와 점수**(아래 사유) |
| `created_at` | 시각 |

**`top_candidates`를 남기는 이유**: 1위만 기록하면 실패했을 때 원인을 구분할 수 없다. 상위 3개를 남기면 두 경우를 나눌 수 있다.

- 정답 문서가 **2~3위에 있었다** → 문서는 있는데 순위를 못 잡은 것 → **표현·랭킹 문제 → 임베딩 도입이 답**
- 정답 문서가 **후보에 아예 없었다** → 문서에 그 내용이 없는 것 → **LLM을 붙여도 소용없고 문서를 보강해야 함**

이 구분이 v2에서 LLM·RAG를 도입할지 판단하는 근거 전부다(11장). 컬럼 하나 차이로 "감으로 도입"과 "로그 보고 결정"이 갈린다.

**`employee_id`는 저장하지 않는다(익명).** 품질 개선에는 누가 물었는지가 필요 없고, 46명 규모 조직에서 "누가 병가 관련 질문을 했는지"가 남으면 그 자체로 민감 정보가 된다.

**정직한 표현**: 대화 원문 중 **질문은 저장된다**. 저장하지 않는 것은 답변 본문(문서 ID로 언제든 복원 가능)과 사용자 식별자다. "대화를 저장하지 않는다"고 말하지 않는다.

`ai_generations` 테이블은 **재사용하지 않는다.** v1은 생성이 없어 `provider`·`model_name`·`generated_output`·`final_output`이 전부 빈 값이 되고, 스키마가 실제와 다른 이야기를 하게 된다. 나중에 LLM을 도입하면 그때 `ai_generations`를 실제 용도로 쓴다.

## 8. 검증·출시 기준

**하드 게이트 (하나라도 실패 시 출시 보류)**
1. **오답 0건** — 잘못된 문서를 근거로 "확정 답변"을 내는 사례가 0. 특히 A4(첨부), C2(신청), F1(기능 목록) 3개 함정 질문과 **E3·E4(권한/403)** 필수 확인. 앞의 3개는 전용 FAQ가 채용·근태 문서를 이기는지, 뒤의 2개는 `권한` 카테고리가 `로그인·계정`에 밀리지 않는지를 본다.
2. **권한 없는 매뉴얼 노출 0건** — 현재 매뉴얼 9개가 전부 전체공개라 실데이터로는 재현 불가. 시드를 건드리지 않고 **자동화 테스트 픽스처**로 검증한다(`target_roles=["SUPER_ADMIN"]` 가상 매뉴얼을 테스트 내에서 생성 → EMPLOYEE 조회 시 후보에서 제외되는지).
3. **정책 질문(F2)이 검색보다 먼저 매칭** — 변형 표현("AI가 대신 결재해줘" 등) 포함.
4. **무관 질문에 근거 없음 응답** — "오늘 점심 뭐 먹지" 같은 입력에 추측 답변이 나가지 않을 것.

**품질 목표**
- 20문항 중 **16개 이상(80%)이 "확정 답변"으로 올바른 근거 제시**. 나머지가 "후보 제시"로 떨어지는 것은 실패로 세지 않되(오답이 아니므로), "근거 없음"은 실패로 센다.
- 위 4개 하드 게이트 전부 자동화 테스트로 고정.

**사용성 점검**(구현 완료 후)
직원 2~3명이 20문항 체크리스트 + 자유 질문으로 사용. 확인 항목: 원하는 답을 찾았는지 / 근거 링크가 쓸모 있었는지 / 자기 표현으로 물었을 때 매칭됐는지.

## 11. 이후 로드맵

순서가 중요하다. **v1.1의 측정과 로그가 v2 도입의 근거가 된다.** 순서를 건너뛰면 "일단 도입해봤다"가 된다.

### v1.1 — 성능 측정과 개선

**전제: 이 서비스는 직원 46명 규모다. 대규모 트래픽 상황이 아니며 그렇게 주장하지 않는다.** 목표는 규모가 아니라 **측정 → 병목 확인 → 개선 → 재측정**의 절차를 실제로 밟는 것이다.

1. **로컬 환경에서만** 부하를 건다(k6 또는 locust). **운영 Supabase에는 절대 걸지 않는다** — 실제 직원 데이터가 있고 커넥션 제한·비용에 바로 부딪힌다.
2. `POST /api/v1/ax/chat`의 **p50 / p95 / 에러율 / RPS**를 기록한다.
3. 병목을 **DB 조회 시간과 매칭 계산 시간으로 나눠서** 측정한다. 예상 병목은 매칭 알고리즘이 아니라 **매 요청마다 문서 30건을 원격 DB에서 가져오는 부분**이다(bigram 점수 계산은 수 ms 수준).
4. 개선안: **문서 집합을 메모리에 캐시**한다. 문서는 거의 변하지 않으므로 효과가 크다.
5. **개선 전후를 같은 조건에서 재측정**해 수치로 비교한다.

**캐시의 트레이드오프(6장과 충돌)**: 6장은 "원본 테이블 직접 조회 → 문서 수정 즉시 반영"을 이점으로 삼았다. 캐시를 넣으면 이 즉시성을 잃는다. 짧은 TTL을 두거나, 매뉴얼·FAQ 저장 시 캐시를 비우는 방식을 함께 검토한다. **성능과 최신성 중 무엇을 얼마나 포기할지가 이 단계의 핵심 판단이다.**

참고: 현재 `DATABASE_URL`은 Supabase pooler(pgbouncer)를 가리키고, `backend/app/db/session.py`의 `connect_args={"prepare_threshold": None}`은 pgbouncer 환경에서 prepared statement를 비활성화하기 위한 설정이다. 커넥션 풀 동작을 함께 이해하고 측정한다.

### v2 — LLM·RAG 도입 (로그 근거로 판단)

v1.1까지 마치고 `ax_chat_logs`가 쌓이면 `top_candidates`로 실패 원인을 분류한다(7장).

- **표현·랭킹 문제가 많다** → 임베딩 기반 검색 도입. 4장의 검색기 경계만 교체하면 되고 API·프론트는 그대로다.
- **문서 부재가 많다** → LLM이 아니라 매뉴얼·FAQ 보강이 답이다.

**문서 30개 규모에서 검색(retrieval)이 필요한 진짜 이유는 컨텍스트 한계가 아니다.** 30개 문서는 최신 모델 컨텍스트에 통째로 넣을 수 있다. 그럼에도 검색이 필요한 이유는 두 가지다.

1. **권한 필터링** — `Manual.target_roles` 때문에 사용자가 볼 수 없는 문서를 LLM 컨텍스트에 넣으면 안 된다. 그대로 정보 유출이 된다. 따라서 LLM 호출 전 권한 기반 후보 축소가 **반드시** 필요하다.
2. **비용과 지연** — 매 질문마다 전체 문서를 전송하면 토큰과 응답 시간이 그만큼 늘어난다.

v2에서 LLM을 붙일 때도 **"검색된 원문 안의 정보만 사용하고 새 정보를 만들지 말 것"** 제약은 유지한다. 이때는 `ai_generations` 테이블(설계는 [[AI_DESIGN.md]])을 실제 용도로 사용한다. 문서 청킹(긴 매뉴얼 `content`를 문단 단위로 분할)도 이 단계에서 검토한다.

기술 선택의 근거를 한곳에 모은다(ADR 성격). **무엇을 골랐는지보다 무엇을 포기했는지가 중요하다.**

| # | 결정 | 대안 | 근거 | 포기한 것 |
|---|---|---|---|---|
| 1 | v1은 LLM 미사용 | LLM으로 답변 생성 | 문서 30개 규모, 할루시네이션 위험 0, 비용 0, 신규 인프라 불필요 | 질문 표현이 다르면 매칭률 하락 |

### 이 프로젝트에서 가장 중요한 판단

**6번이다.** "전자결재에 파일을 첨부할 수 있나요?"라는 질문에 시스템이 **"네, 첨부할 수 있습니다"라고 틀린 답을 할 구조**임을 구현 전에 발견했다. 전체 30개 문서에서 "첨부"라는 단어가 채용 매뉴얼 2곳에만 있었기 때문이다.

이때 선택지는 두 가지였다. 매칭 알고리즘을 정교하게 만들어 피해가거나, 없는 문서를 만들거나. **알고리즘으로는 풀 수 없는 문제였다** — 시스템에 없는 기능이라는 사실이 어느 문서에도 적혀 있지 않았으므로, 어떤 검색 방식을 써도 "없다"는 답은 나올 수 없었다.

→ 코드를 짜기 전에 FAQ를 먼저 추가했고, 그 FAQ에 "채용 포스터 첨부와는 다른 기능"이라는 문장을 넣어 오매칭까지 함께 막았다.
