- 프로젝트명: MS FlowHub

- 성격: 기업 업무 흐름을 축소 구현하는 취업 포트폴리오 프로젝트
- 목적: 전자결재를 중심으로 직원·조직 관리와 채용 요청 업무를 연결하고 반복 업무를 체계화한다.

## 기획 배경과 해결 문제

부서별 도구가 분리되면 요청 정보가 반복 입력되고 승인 상태와 후속 업무의 연결이 끊긴다. MS FlowHub는 공통 직원·부서·역할 데이터와 전자결재 엔진을 공유하여 채용 요청부터 공고 생성까지 추적한다.

## 사용자 역할

일반 직원, 팀 관리자, 인사 관리자, 최고 관리자. Supabase Auth 로그인 후 FastAPI 서비스가 직원과 역할을 다시 조회해 권한을 판단한다.

## 모듈 구성

1. 전자결재: 공통 핵심 엔진, 단일 결재자, 상태 전환과 이력
2. ATS Lite: 승인된 채용 요청 기반 공고
3. 직원 매뉴얼: 업무 기능 사용 안내와 역할별 관리

모듈은 분리하지만 공통 사용자, 부서, 권한, 결재 데이터를 공유한다. 전자결재와 채용 요청은 실제 업무 흐름에 맞게 구현한다.

## 프로토타입 범위

- 직원·부서·역할 전환, 대시보드, 접근 가능 모듈 표시
- 전자결재 작성·상신·승인·반려·의견·상태·이력·알림
- 승인된 채용 요청에서 공고 생성
- 직원 매뉴얼 목록·검색·상세와 역할별 관리
- Supabase PostgreSQL, Alembic, Seed, 오류 처리, 핵심 테스트

## 프로토타입 제외 범위

실제 이메일 발송, PDF 분석, OCR, RAG, 벡터 DB, n8n, 다단계 결재, WebSocket 알림, 실제 개인정보·기밀, Docker, 모바일 앱, 자동 채용 결정.

## 주요 업무 정책

- 작성자와 결재자는 달라야 한다. 자기 결재는 프로토타입에서 금지한다.
- 결재는 허용된 상태 전환으로만 변경하며 처리 완료 문서는 재처리할 수 없다.
- 승인되지 않은 채용 요청은 공고로 만들 수 없다.
- AI는 승인·반려·채용 결과·실제 발송을 결정하거나 실행하지 않는다.

## 성공 기준과 완료 기준

직원·조직 관리와 채용 요청 시나리오를 로그인부터 끝까지 시연하고, 데이터가 Supabase PostgreSQL에 저장되어야 한다. 프론트엔드는 FastAPI만 호출하며 Seed는 멱등적이어야 한다. 금지된 상태 전환이 차단되고 핵심 Backend 테스트가 통과하며 README/UPDATELOG가 실제 상태와 일치해야 한다.

## 장기 목표와 확장 가능성

프로토타입 이후 실제 인증, 다단계 결재, 강화된 권한·감사, 이메일 연동, 운영 DB 분리, 관측성과 배포 자동화를 단계적으로 도입한다. 현재 결과물을 실제 기업용 완제품으로 과장하지 않는다.
